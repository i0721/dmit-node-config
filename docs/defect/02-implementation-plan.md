## 范围与总体方案

保留 Rust 配置、确定性快照、校验收据与事务恢复核心，完成清单建议的路线 A 产品交付，同时提供可审计的首次配置向导。系统软件、DNS、证书、WARP 注册仍使用官方工具和分层部署步骤，不能把清单中的“设计流程”误实现为不可预览的自动系统改写。

范围包括正式发布、两个 Linux 架构、可信安装、自升级、安全卸载、诊断与状态、配置向导与迁移规则、自动验证和全部指定文档。APT 仓库与独立文档站只做交付评估，清单没有要求建设公共软件源或站点。继续使用 GitHub 开源库，密码、网络协议、签名验证及 SBOM 均复用成熟工具。

本次不更新线上代理依赖，不删除线上服务、不在生产 VPS 注入故障；测试使用临时目录、隔离虚拟机或 CI。所有发布和外部仓库状态必须用实际结果验收，缺乏凭据或执行环境时不能标为完成。

## 技术设计

1. 发布 v0.2.0：固定 Rust 1.99.1、Cargo.lock；原生 amd64/arm64 构建与测试，归档二进制、许可证、依赖许可、SBOM、构建信息。GitHub OIDC + Sigstore/cosign 为 SHA256SUMS 签名，GitHub artifact attestations 绑定资产与提交。标签发布受全部检查及集成测试约束。
2. 安装器：仅处理 nodectl，不隐式安装代理依赖。版本为必填输入；区分两个架构，HTTPS 获取资产，先校验签名的签发者与工作流身份，再校验 SHA256，临时文件解包、二进制自检、同目录原子替换。dry-run 仅展示动作。旧程序在本地版本备份中保留；自升级调用相同安装路径，不自行实现签名算法。
3. doctor/status：诊断独立项，失败后继续收集，给出修复建议，支持 JSON。未初始化也能检查系统。status 不输出凭据，展示 current/previous、事务、服务、收据与证书到期状态。诊断默认只读。
4. setup：交互和非交互两种入口，输入域名、别名、IP、证书目录、WARP 开关；preview 不写文件，显式执行后原子写入同一 node.toml/secrets.json。不得覆盖已初始化输入；已有配置使用显式编辑或迁移。
5. 迁移：明确唯一受支持 schema v1，当前版本迁移为校验后的无损操作；未知新旧版本拒绝并保留原文件。未来迁移须实现备份、验证与失败恢复，不能用默认值覆盖未知结构。
6. 卸载：首次应用前持久化原始入口和服务状态，保留初始备份。uninstall 预览显示恢复范围，执行时确认入口仍由本项目管理、验证备份，先写可恢复日志，恢复原文件/符号链接/启用状态/运行状态并验证。原始状态不完整则拒绝；证书、WARP、配置、快照与程序默认保留。recover 同样处理卸载中断。
7. 测试：单元与命令测试检查失效/篡改/锁/权限；安装器本地签名夹具验证成功及拒绝路径；干净 Debian 12/13、Ubuntu 24.04/26.04 使用隔离 systemd 环境，双架构实际运行；真实 Nginx/Xray 验证 TCP、UDP、UDS、H2/H3、三握手，并在切换各阶段注入失败验证恢复。发布自检针对最终归档中的二进制。
8. 文档与社区：分层导航、正式架构和决策、泛化 example.com 与文档地址；删除公开截图中的真实环境材料并替换为明确标记的通用示意，不将真实截图伪装为通用实拍。链接/锚点检查、密钥扫描、贡献与安全政策、Issue/PR 模板进入门禁。
