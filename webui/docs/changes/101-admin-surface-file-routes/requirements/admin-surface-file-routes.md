# Admin Surface 文件路由能力需求

## 客户目标

让 Admin 业务能力以「Plugin + 文件路由」的确定性方式进入统一前端，而不是继续在 Host
手工堆叠路由、导航与 Shell 分支。业务作者只描述页面与静态元数据，导航、层级、面包屑、
命令与承载能力由统一模型和生成管线推导。

## 使用场景与可验收行为

### 场景 A：业务作者新增一个带列表的 Plugin

- 在插件目录创建 `plugin.ts`（声明 `pluginId` 与 `mount`）与 `routes/page.tsx` 页面。
- 在页面旁创建 `route.meta.ts` 声明 navigation（导航名、标签、分组）与页面标题。
- 运行一次生成命令后，该页面即可通过浏览器直接访问，并出现在 Shell 导航与命令检索中。
- 验收：生成后页面可访问；导航分组可见；重复运行生成命令不改变任何文件（确定性）。

### 场景 B：业务作者新增详情/编辑/创建等子页面

- 只写页面与静态元数据；不声明导航的子页面自动继承最近可见祖先导航，页面层级
  （面包屑、canonical parent）由文件树自动派生。
- 页面之间使用符号目标（route id + 参数）跳转，不允许手写 URL。
- 验收：详情/编辑在浏览器中可达；面包屑与「当前所在导航」正确；离开插件层级无孤儿页面。

### 场景 C：引用插件之外的目标或动态路由

- 动态段路由（例如 `[id]`）在文件路由与编目中合法，但当前静态导出宿主不能承载：
  生成 Host 入口之前必须明确失败并说明原因，不允许生成一个必然 404 的占位。
- 跨插件引用、覆盖缺少说明、重复 id/路径等错误在生成时直接失败。
- 验收：生成命令返回非零并列出具体违规；错误信息可定位到插件与路由。

## 范围

- 本阶段交付：框架契约、Surface 私有边界、参考插件、生成器、Registry、治理门禁、
  Host 最小装配（Navigation Port、i18n 聚合、Registry 派生导航）与参考插件浏览器验收。
- 非目标：既有页面与既有静态导航迁移、完整 Shell 视觉重构、Legacy Navigation 冻结、
  Shell CSS、Host 全量路由迁移（后续 Migration Phase）。

## 约束

- 唯一真实 Router 是 Next.js App Router；任何层不得另起路由、历史或 pathname 解析。
- 浏览器 API（history、location、window）不得进入共享代码；动态能力全部通过 Host Port 注入。
- 生成物视为源码：不可手改、必须可复核、不得被格式检查二次修改。
